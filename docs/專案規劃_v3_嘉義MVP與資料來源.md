## 3. 重新設計的運算流程：本機優先、5090 批次短跑

### 3.1 設計原則
1. **5090 時間寶貴 → 在 5090 上只跑「已在本機驗證過」的批次任務。** 不在 5090 上除錯。
2. **所有 5090 任務封裝成「一鍵包」**：複製資料夾（USB / 外接硬碟 / 雲端）→ 雙擊 `run_on_5090.bat` → 結果寫入 `outputs\` → 帶回本機。
3. **斷點續跑 + 進度檔**：每個批次可隨時中斷；以 `done.jsonl` 記錄已完成項目；時間到了就停，下次接著跑。
4. **每個任務限時模式**：`run_on_5090.bat --max-minutes 90`，到時自動安全收尾並輸出狀態報告。
5. **離線安裝**：因無遠端、可能網路受限，預先製作離線環境（`uv pip download`/wheelhouse + Ollama 模型檔 + HuggingFace 模型快取）放入包內；5090 機器第一次執行跑 `check_env.bat`（自動測 CUDA、PyTorch、模型是否載入、輸出 GPU 型號）。
6. **本機 smoke 測試必過**：每支腳本有 `--smoke`（50 張圖 / 1000 筆資料、CPU 可跑）。

### 3.2 本機（無 GPU）與 5090 任務分配

| 任務 | 本機 | 5090 |
|---|---|---|
| 孔位 CSV 篩選嘉義、join 檔名 | ✅ | |
| OCR/LLM 解析程式開發、**50–100 張**小樣本驗證與準確率 | ✅（CPU 慢但可跑） | |
| **嘉義柱狀圖批次 OCR + 校對（數千張）** | | ✅ **主要吃 GPU 的工作** |
| 水文地質 API / 地質雲 / DEM / TEC 下載 | ✅（需網路） | |
| 特徵工程、切分、洩漏測試 | ✅ | |
| Baseline（RF/LightGBM CPU） | ✅ | |
| GBDT-GPU、神經網路、Optuna、體素推論 | | ✅ |
| 視覺化、報告 | ✅ | |

### 3.3 5090 時間估算與預算（先在本機量測後填表）
- 本機量測：每張圖處理秒數（CPU）。再依經驗 5090 實測一次短跑（10 分鐘）取得 GPU 秒數/張，推算批次所需時數。
- 嘉義約 5.5k 孔，其中**僅取 ≥30 m（4.3k 孔）優先**；若時間不足，優先 ≥60 m（2.5k 孔）與全部 ≥100 m。
- **OCR 排序策略**：深孔優先 → 淺孔次之（深孔對 1 km 目標價值最高）。
- 預留 5090「機會視窗」清單（每次視窗要做的事先排好，如：視窗 1 = 環境驗證 + OCR 試跑；視窗 2 = OCR 批次；視窗 3 = 模型訓練；視窗 4 = 全區推論）。

## 4. 修訂階段計畫（嘉義 MVP）

### Phase 0：準備（第 1 週）
- [ ] 建立 repo / `uv` / config 框架 / `--smoke` / `done.jsonl` 斷點機制 / `run_on_5090.bat` 模板。
- [ ] **驗證所有資料來源**：呼叫 `hydro.geologycloud.tw` 三個 API（對嘉義範圍）、地質雲 Swagger、GeoTEX、DEM；記錄回傳欄位、筆數、授權 → `docs/data_sources.md`。
- [ ] 寄出申請信（中油探採、地調所諮詢），記錄寄信日與窗口。
- [ ] 篩選嘉義孔位（bbox → 建議再依行政區/地質分區細化）；產生 `chiayi_holes.csv`，標示每孔是否已有柱狀圖/岩心照片（掃描 H 槽檔名）。
- [ ] 座標工具 `crs.py`（TWD67/TWD97/WGS84）+ 測試。
- [ ] 修正 GeoLogParser 輸出亂碼（UTF-8）。
- [ ] 預先打包離線環境與模型；排定第一次 5090 視窗要做的 `check_env`。

### Phase 1：鑽孔資料庫（第 2–5 週）
1. **本機**：從嘉義柱狀圖隨機抽 **150–200 張** 建立人工驗證集（座標、分層深度、岩性），量測 GeoLogParser 各欄位準確率；試 VLM 路線 vs 現行 OCR+規則的對比（本機僅小樣本，必要時使用 5090 視窗 1 跑對比）。
2. **座標雙保險**：以 `proj_no+hole_no` join CSV 座標/高程/孔深為**主**，OCR 座標僅作交叉檢查。
3. **5090 視窗**：批次解析嘉義柱狀圖（深孔優先，斷點續跑）。
4. **水文地質 API 資料**：直接匯入 `RockRecord`（岩性紀錄），**無需 OCR**，將岩性文字轉 L1 粗類；與工程鑽孔合併為統一 schema（`source` 欄位標記來源）。
5. **標籤標準化**：L1 粗類（回填 / 黏土-粉土 / 砂 / 礫 / 互層 / 軟岩 / 硬岩），組合規則（「砂質泥岩」「泥質砂岩」等）；規則 vs 人工驗證集評估；不一致者人工複核。
6. QC：座標出界、高程與 DEM 差過大、深度非單調。
7. 輸出 `boreholes.parquet` / `strata.parquet` / `lith_samples.parquet`。

**驗收**：驗證集欄位準確率 ≥ 90%；嘉義可用孔數與深度分布圖；標籤覆蓋表（見 §5）。

### Phase 2：特徵資料（第 3–7 週，與 Phase 1 平行）
- TEC 速度模型擷取嘉義範圍 + 三線性取值；Vp/Vs、梯度、鄰近統計；**確認最大深度是否到 1 km**。
- 地質雲：地質圖單元、斷層距離；DEM：高程、坡度、離海距離。
- 水文地質井測（電阻/伽瑪）：作為輔助特徵或獨立驗證。
- 強震場址（SSR/HVSR，依 `code_artifact.md` 改善項）：嘉義附近測站，作獨立驗證（可選，不阻塞主線）。

### Phase 3：資料集與切分（第 7–8 週）
- Group K-Fold（鑽孔）+ **空間 block CV**（如 5 km）+ **獨立 hold-out 區**（嘉義東部山區或某鄉鎮完全不參與訓練）。
- 以 **深度帶（0–50 / 50–200 / 200–1000 m）** 分別報告指標。
- 自動測試確認無鑽孔跨 fold 洩漏；parquet 存檔。

### Phase 4：模型（第 8–13 週）
- **本機**：去洩漏 baseline（RF/LightGBM CPU）、規則基準線、特徵消融。
- **5090 視窗**：LightGBM/XGBoost-GPU + Optuna、序列模型（1D-CNN/BiGRU，以整孔深度序列為輸入）、不確定性（ensemble/conformal）。
- 每個 5090 視窗前先在本機 `--smoke` 通過；視窗內只跑 config 指定的實驗清單，並限時。
- 深度帶專屬 / 層級分類：深層用粗類。

### Phase 5：嘉義 3D 推論（第 12–15 週）
- 網格：水平 250–500 m；垂直 0–100 m 每 5 m、100 m–1 km 每 25–50 m；DEM 以上不預測。
- **5090 視窗**：分塊推論 → Zarr；輸出類別機率、熵、距最近鑽孔距離。
- 鑽孔體素以觀測覆蓋（硬資料條件化）；深層外推區標示。
- 衍生：基盤面深度、軟弱層厚度、信心圖。

### Phase 6：視覺化與成果（第 14–18 週，本機）
- 剖面（疊實際鑽孔柱）、柵欄圖、基盤面、PyVista 3D、信心圖；科展圖表（混淆矩陣、SHAP、消融、預測 vs 實際）。
- 與 3D 地質模型/文獻基盤面比較；敏感度與限制分析。
- **MVP 可交件點**。

### Phase 7：擴展全台（第 18 週後）
- 依地質分區複製流程；先做**水文地質資料齊全的平原區**（嘉南 → 濁水溪 → 屏東），山區最後；跨區泛化測試。

## 7. 風險補充

| 風險 | 對策 |
|---|---|
| 水文地質 API 實際不可用或欄位不符 | 第一週驗證；備案：網頁圖台手動匯出 / 洽詢地調所 |
| 5090 時間不夠跑完 OCR | 深孔優先、分批視窗、斷點續跑；優先使用 API 取得的結構化資料減少 OCR 量 |
| 5090 離線環境缺套件導致浪費時間 | 預先離線打包 + `check_env.bat`；每次視窗前本機模擬「乾淨環境」安裝測試 |
| 本機 CPU 跑 LLM/VLM 過慢 | 本機只做小樣本；LLM 校對可改為批次在 5090 跑 |
| 中油資料申請失敗 | 保底策略（§2.4）：粗類 + 基盤面 + 外推標示 |
| 柱狀圖版式多樣導致 OCR 準確率低 | 驗證集分版式統計；低信心者進人工複核佇列；座標改用 CSV join |
| 授權/使用條款 | 每個資料源記錄於 `docs/data_sources.md` |
